# ThunderTyping — Project State & Roadmap

**Read this file first.** It exists so any AI agent or developer (not just the one who wrote it) can pick up this project cold and be productive immediately, without re-asking the human basic questions about scope, stack, or decisions already made. Keep it updated as the source of truth for "what's done" and "what's next." If you finish work, update the relevant sections before ending your session.

## What this project is

A typing-speed-test website (MonkeyType-style) aiming for large organic Google traffic, monetized via Google AdSense. Long-term ambition: "world's best typing platform," but development proceeds in deliberate phases — **do not jump ahead to multiplayer/accounts/backend/games until explicitly prioritized below.**

- **Brand name**: ThunderTyping
- **Current phase**: Frontend-only MVP. No backend, no accounts, no database. Everything persists to `localStorage`.
- **Language**: English only (architecture supports adding more later, see `src/data/words/` and `src/data/quotes/`).
- **Design**: Minimalist, MonkeyType-inspired — the typing area is the visual star, chrome stays out of the way. Five built-in themes (Dark default, Light, Midnight, Forest, Sunset) via a theme picker in the header, all color changes transition smoothly except per-character typing feedback (deliberately instant — see Architecture).

## Tech stack & conventions

- Next.js 16 (App Router, Turbopack), React 19, TypeScript (strict), Tailwind CSS v4 (theming via CSS variables in `globals.css`, **no `tailwind.config.ts`** — Tailwind v4 doesn't need one here).
- `zustand` (+ `persist` middleware) for durable, low-frequency state (user settings). `useReducer` for the high-frequency typing engine state (not zustand — see Architecture).
- `motion` (formerly Framer Motion) for animation — imported from `motion/react`, **not** the bare `motion` package root (that resolves to the vanilla-JS DOM API, not React components/`layoutId`).
- `lucide-react` for icons, `clsx` (wrapped as `cn()` in `src/lib/utils/cn.ts`) for conditional classnames.
- `src/` directory, `@/*` path alias to `./src/*`.
- Conventions mirrored from a sibling project at `../Git-Review` (Next.js 16.3.4, same Tailwind v4 pattern) for consistency, though the two projects are unrelated products.
- Git repo initialized at the project root (was previously un-versioned). Commit as you go — meaningful, scoped commits, not one giant dump.
- Dev server: `.claude/launch.json` in the **sibling `Git-Review` directory** has a `"thundertyping"` entry using `npm --prefix ../thundertyping run dev -- -p 3002` (the harness's `preview_start` tool reads `launch.json` from the primary working directory, which is `Git-Review`, not this repo — this is an environment quirk, not a design choice). In practice a dev server for this project may already be running on port 3001 or 3002 via an external auto-restart supervisor in this environment — check `ss -ltnp | grep 300` before assuming you need to start one.

### Known issues fixed this session (context for why the code looks the way it does)
- **Results screen's accuracy % and its "correct/incorrect" breakdown could contradict each other.** Reported by the human ("miscounted stats" when typing commas), reproduced precisely: custom text "cat", typed with one backspaced-out mistake (typed "ca" + wrong "x", backspaced, then correct "t") showed **"3 correct, 0 incorrect" in the breakdown but 75% accuracy** — impossible for those two numbers to both be right. Root cause: `charTally.correct`/`.incorrect` were computed from each word's *final* character state at commit time, while accuracy/rawWpm were computed from `correctKeystrokes`/`incorrectKeystrokes` (the full keystroke history, including the backspaced "x"). A corrected mistake vanished from one metric but not the other. The comma connection: punctuation marks are unfamiliar mid-word (no space before them), so users mistype-then-correct them more often than letters — same bug, just triggered more visibly there. Fixed by removing `correct`/`incorrect` from `CharTally` entirely and having the results breakdown read `correctKeystrokes`/`incorrectKeystrokes` directly (the same numbers accuracy is computed from), so the two can never disagree again. `CharTally` now only tracks `extra`/`missed`, which are inherently final-state concepts with no keystroke-history equivalent.
- **Live WPM could spike to absurd values (e.g. "12000 wpm") in the first instant of a test.** The human caught this on video. Root cause: `netWpm = correctChars / 5 / minutesElapsed` is mathematically unstable when `minutesElapsed` is a few milliseconds — one correct keystroke at 5ms elapsed implies a ~12,000 WPM pace. Fixed by flooring the time denominator at `MIN_LIVE_WPM_WINDOW_MS` (1000ms) for both the live display (`stats.ts`'s `calculateLiveWpm`) and the consistency-score sampling in the reducer's `TICK` case (samples from the first second are skipped entirely rather than computed, so they don't pollute the consistency calculation either). The final result always uses true elapsed time — only the *live, in-progress* number and *sampling* are floored/skipped.
- **UI jumped/glitched the instant typing started.** Also caught on video. Root cause: the config bar was conditionally mounted/unmounted (`{status !== "running" && <ConfigBar/>}`), so when it exited, the flex gap it occupied collapsed instantly and everything below (stats bar, word stream) snapped upward — jarring even though the config bar's own fade-out was smooth. Fixed by keeping the config bar permanently mounted and crossfading it with the live-stats bar inside one fixed-height slot (`relative` wrapper, stats bar `absolute` centered over it) in `typing-test.tsx` — the slot's height is always the config bar's natural height, so nothing below it ever moves. Verified via `getBoundingClientRect()`: the word-stream's position is bit-for-bit identical before and after a test starts.
- **Turbopack dev server can serve a stale compile error after a file edit** (observed: it reported a "defined multiple times" error for constants that, on disk, were only ever defined once — the fix had already landed). A one-shot `npm run build` confirmed the source was correct the whole time. If the dev server's error overlay disagrees with a fresh `npm run build`, trust the build and restart the dev server (`rm -rf .next` then `npm run dev`) rather than "fixing" code that isn't broken.
- **Hydration mismatch**: the engine's initial word list uses `Math.random()`. If the interactive `<TypingTest>` component were server-rendered like a normal client component, the server's random words would differ from the client's, corrupting hydration. Fixed by wrapping it in `next/dynamic(..., { ssr: false })` via `src/components/typing-test/typing-test-client.tsx`. The static shell (h1, intro, JSON-LD) around it still renders server-side for SEO.
- **Double word-regeneration on mount**: React Strict Mode (on by default in Next.js dev) double-invokes effects, which defeated a naive `useRef(true)` "skip first run" guard in `typing-test.tsx`. Fixed by comparing the memoized `config` object by reference instead of using a boolean flag (see the `lastAppliedConfigRef` pattern in `typing-test.tsx`) — this is the robust pattern, not a hack; keep it if you touch that file.
- **Custom mode + reload = stuck blank test**: `mode` is persisted via zustand, but `customText` deliberately isn't (it's ephemeral component state — see Architecture). A reload while in custom mode used to restore `mode: "custom"` with no text behind it, leaving the engine with an empty word list and no visible way to recover short of manually changing modes. Fixed as part of the settings-store rehydration validation: a persisted `"custom"` mode is treated as absent and falls back to the default.
- If you see a "space key" not registering during **automated browser testing** in this environment, that's a known quirk of the browser automation tool used in this session (its `key` action for `"space"` dispatches a malformed event with empty `key`/`code`/`which`) — not an app bug. Verified via `Tab` (which dispatches correctly) and via manually constructing a proper `KeyboardEvent`. Real users pressing a physical spacebar are unaffected.
- **`requestAnimationFrame` does not reliably fire in this automation environment** when the Browser pane isn't actively displayed/composited — confirmed by a direct test (a double-rAF promise hung for the full 30s tool timeout). This has a real consequence for testing (not for real users): `motion`'s `AnimatePresence` exit animations reach their final CSS state (e.g. `opacity: 0`) but the element can be left mounted in the DOM instead of being removed, because Motion's unmount bookkeeping depends on rAF-driven completion callbacks. Observed on both the config-bar exit and the custom-text-modal exit. This is standard, heavily-used library behavior (`AnimatePresence` exit-unmount) that should work correctly in any normally-rendered browser tab — it could not be fully verified end-to-end in this session's automation environment specifically. Worth a quick manual spot-check in a real browser at some point; not something to "fix" based on this session's evidence alone.

### Not built yet (by design, not oversight)
- No settings modal (Escape currently just blurs the input). Theme is reachable via the header toggle. A settings modal (sound toggle, more themes) is a reasonable near-term addition once there's more than 2 themes / real sound assets.
- No sound effects (keystroke sounds) — `soundEnabled` exists in the settings store but nothing plays yet.
- No custom favicon (still the Next.js default `favicon.ico`); OG image is now handled (see above).
- No real AdSense integration — `AdSlot` component (`src/components/layout/ad-slot.tsx`) renders placeholders until `NEXT_PUBLIC_ADSENSE_CLIENT_ID` is set; wiring a real AdSense account is an external action requiring the human (account creation/approval), not something an agent can do.
- No focus-trap in the custom-text modal (Tab can leave the dialog while it's open) — verified the browser's native focus-visible outline itself is intact everywhere (Tailwind v4 Preflight doesn't suppress it; confirmed by reading the compiled CSS rather than relying on this environment's unreliable synthetic-focus testing), but full modal focus-trapping wasn't implemented. Low risk given the modal is simple (one textarea, two buttons) but worth doing if a more complex modal is added later.
- Screen-reader typing experience is fundamentally limited: the interaction model (a real but visually-hidden `<input>` driving a custom visual rendering) is the same pattern virtually all typing-test sites use, and it means a screen-reader user gets no real-time spoken feedback about correctness while typing. This is a known, hard, industry-wide limitation of this app category, not something fixed by a small patch — flag it if accessibility becomes a stated priority, since solving it properly likely means a fundamentally different interaction mode for screen-reader users, not a tweak.
- Unicode edge case: character comparison in the engine indexes strings by UTF-16 code unit, not by grapheme cluster. Custom text containing characters outside the Basic Multilingual Plane (most emoji) would render slightly oddly (each surrogate half treated as its own "character") but will not crash the app — `SET_TYPED` already guards against an undefined target word. Deferred as low-priority/rare rather than risking a refactor of core, verified-working comparison logic for it.

## Architecture notes (read before modifying the engine)

- **Engine state** (`src/lib/typing-engine/use-typing-engine.ts`) is a `useReducer`, not zustand — it mutates on every keystroke (high-frequency, subtree-local), whereas zustand (`src/lib/persistence/settings-store.ts`) holds durable, low-frequency, cross-cutting state (settings, theme). Don't move engine state into zustand; don't move settings into the reducer.
- **Keystroke capture** is a real, focused, offscreen `<input>` (`hidden-input.tsx`), not raw `keydown` — needed for IME composition and mobile virtual keyboards. Space/Tab/Escape are intercepted in `onKeyDown`; paste is blocked entirely (`onPaste` preventDefault) so pasted text can't silently distort keystroke-based WPM counting.
- **`correctKeystrokes`/`incorrectKeystrokes` are monotonic** — never decremented by backspace, and they are the **only** source for accuracy/WPM/raw-WPM *and* the results screen's "correct"/"incorrect" breakdown (see the fixed bug above — they used to come from two different places and could contradict each other; now there is exactly one source of truth for those two numbers). This is intentional (standard typing-test convention: a mistyped-then-corrected character still counts as effort for raw WPM/accuracy). The counting logic loops over every newly-inserted character (not just "the" new character) so any multi-character insertion is credited/blamed correctly. Don't "fix" this into a diff-based recount, and don't reintroduce a separate correct/incorrect tally derived from final word state.
- **`charTally`** now only tracks `extra`/`missed` — both inherently final-state concepts (what's left over in the text you actually submitted) with no sensible keystroke-history equivalent, unlike correct/incorrect. It's accumulated incrementally at word-commit/finish time, not derived by re-scanning `wordStates` at the end — this was a deliberate simplification vs. the original plan's "prune old words from memory" idea. At realistic max test length (120s time mode, worst case a few hundred words), unpruned `wordStates` is cheap enough that pruning would add reducer complexity for no real benefit. If a future mode allows much longer tests, revisit this.
- **One engine, all four modes** — time/words/quote/custom share the same reducer and rendering path, diverging only in word-supply strategy (infinite-regenerating vs. fixed) and completion condition (timer vs. last-word-exact-match). Don't fork into separate engines per mode.
- **Word/quote data is fully static** (`src/data/words/english-1k.ts` — actually ~360 words, not literally 1000; `src/data/quotes/english-quotes.ts` — ~26 public-domain quotes). Adding a language later means adding a new data file + extending the `mode`/language config, not rewriting the engine.
- **Shared option constants live in `engine-types.ts`** (`TIME_DURATIONS`, `WORD_COUNTS`, `QUOTE_LENGTHS`) — both `settings-store.ts` and `test-config-bar.tsx` import from there. They used to be independently redefined in both files; if you find yourself typing out `[15, 30, 60, 120]` anywhere, you're about to reintroduce that duplication.
- **Persisted data is never trusted blindly.** `settings-store.ts`'s `merge` option validates every field against its allowed values on rehydration; `results-store.ts`'s `getPersonalBest` validates the parsed shape before returning it. If you add a new persisted field, add it to the corresponding validator — don't just trust `JSON.parse`.
- **Theming**: 5 themes defined as CSS var blocks in `globals.css` (`:root` = dark default, `[data-theme="x"]` overrides), registered in `THEMES` in `themes.ts` (id, label, small swatch for the picker UI). Adding a theme is one more CSS block + one more array entry — the picker, validation (`settings-store.ts`), and anti-flash script all read from that data, nothing else needs touching. **`--correct` is the bright foreground color in every theme, not green** — this matches MonkeyType's convention (a correctly-typed character becomes the "main" bright color; only mistakes get a distinct color) and was an explicit design request, not an oversight. A global `* { transition: background-color, border-color, color 0.2s }` in `globals.css` makes theme switches fade smoothly everywhere — **except** per-character spans in `word-stream.tsx`, which carry a `char-instant` class (`transition: none`) so live typing feedback never lags behind a keystroke. If you add new themed UI, you get the smooth transition for free; if you touch the character-rendering path, keep `char-instant` on it.
- **The config bar and live-stats bar never unmount** — they're crossfaded (opacity + `pointer-events`) inside one `relative` wrapper in `typing-test.tsx`, with the stats bar `absolute`-positioned over the config bar's natural footprint. This was a deliberate fix for a real layout-shift bug (see "Known issues fixed"); don't go back to conditionally mounting either one, since that's exactly what caused the word-stream to jump.
- **`SUPPORT_EMAIL` in `src/lib/seo/constants.ts` is a placeholder** (`hello@thundertyping.com`, same placeholder domain as `SITE_URL`) — it is not a real, monitored inbox. It's referenced from `/privacy` and `/terms`. Replace it with a real address before those pages are relied upon for anything (including AdSense review, which expects a working contact method).

### SEO / Organic Growth
Full competitive/keyword research was done in an earlier session (see condensed summary below). Key strategic takeaways:
- **Don't chase head terms** ("typing test", "wpm test") pre-launch — zero domain authority, dominated by Monkeytype/10FastFingers/TypingClub. Build long-tail + topical authority first.
- **Real product-level wedge**: Monkeytype-grade UX + genuinely good **mobile** support (NitroType/TypeRacer both have poor mobile UX — a gap) + light beginner guidance + real accessibility, wrapped in a legitimate content layer Monkeytype doesn't bother building (it's donation-funded, no SEO incentive).
- **Danger zone**: Google's "scaled content abuse" policy (active, enforced through 2026) specifically calls out templated duration/variant/language page patterns as a common abuse example **in this exact niche**. Any programmatic page set (e.g. `/typing-test/1-minute`, `/typing-test/5-minute`) needs genuinely differentiated copy per page, not keyword-swapped templates, or it risks tanking the whole domain's trust under Google's site-wide helpful-content evaluation.
- **INP (Core Web Vitals) is unusually high-stakes here** — the entire product IS keypress-to-render latency, not just an SEO checkbox. Keep keydown handling lightweight, avoid blocking work per keystroke, keep AdSense script loading isolated from the typing input path once real ads are added.
- Priority content build order now that `/about`/`/privacy`/`/terms` exist: (1) a couple of duration-variant pages with real differentiated copy, (2) genuinely useful informational guides ("what's a good WPM for X job", "how to improve typing speed", touch-typing basics) to build topical authority + internal linking, (3) job/exam-context long-tail pages (recurring, lower-competition demand), (4) shareable/downloadable results certificate (Ratatype's certificate feature is a proven, useful pattern for résumé/job-application use), (5) non-English expansion — flagged as a strong future opportunity, especially Hindi + Indian government-exam typing-test queries (recurring, well-defined demand), but out of scope for the English MVP.
- Full research report (competitor breakdown, keyword clustering, sourcing) is preserved in the session transcript that produced it; re-run this research periodically since the space evolves (SERP composition, AdSense policy, Core Web Vitals thresholds all shift).

### Growth / Retention / Monetization

## Operating model notes (for whichever agent picks this up)

This project was set up under an ambitious "operate as an autonomous 5-lens product organization" instruction from the human (Product/Architecture, Frontend/UX, SEO, QA, Growth), later followed by a "keep going through review/polish phases without stopping" directive. Important honesty notes carried forward from those conversations, so you don't re-promise things that aren't real:

- **There is no standing, always-on scheduler running this project every N hours**, unless one has actually been configured via this platform's scheduled-task tooling — check `mcp__scheduled-tasks__list_scheduled_tasks` (or equivalent) before claiming a cycle is scheduled, don't assume.
- **A local dev process cannot run while the machine is off or the harness isn't open.** Don't imply otherwise.
- Treat "I built this" / "I verified this" / "I recommend this" / "this is blocked on the human" as distinct claims — don't blur them. This file tries to model that: the "Done and verified" section lists only things actually exercised in a browser this session, and the "known issues" section is honest about what this specific automation environment could and couldn't reliably test (see the rAF/AnimatePresence note).
- Prefer fixing a small number of real, high-value things well over generating a large volume of speculative work (pages, features, tests) to look productive. The SEO research above explicitly flags that this exact niche is a magnet for exactly that failure mode (thin programmatic content) — don't repeat it. When asked to "keep going" through review phases, that means actually finding and fixing real issues (this session found and fixed ~10: a stuck-blank-screen bug, missing paste-blocking, missing persisted-data validation, missing pages, missing a11y attributes, dead code, duplicated constants), not inventing busywork.
