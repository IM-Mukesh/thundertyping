# HERO TYPING AUTH ROUTE RESTORATION REPORT

### Root cause
The original login route was physically located at `src/app/auth/login/page.tsx` (outside the locale folders). However, the existing proxy middleware (`src/proxy.ts`) was designed to assume that any request lacking a locale prefix is intended for English, automatically rewriting paths like `/auth/login` to `/[DEFAULT_LOCALE]/auth/login` (i.e. `/en/auth/login`). Because there was no `src/app/[locale]/auth` directory for the App Router to match against, Next.js returned a `404 Not Found`.

### Route architecture
I safely moved the `src/app/auth` directory into `src/app/[locale]/auth` so that it became a standard locale-aware route. This elegantly resolved the proxy rewrite (since `/en/auth/login` is now a valid physical route) and natively introduced support for `/de/auth/login`, `/es/auth/login`, and `/pt-br/auth/login` without requiring duplicate implementations or changing proxy logic.

### Authentication
The existing Google Identity Services implementation (client-side `signInWithGoogleIdToken`) remains securely in place and unaltered. The `GoogleSignInButton`, `useAuth` hook, and Supabase initialization were completely preserved. The login page correctly renders independently of the main content repository, meaning it does not crash if localized vocabulary or lesson seed data is missing.

### Callback
The primary callback path at `/api/auth/callback` remains completely stable and functional. It is explicitly excluded from locale rewrites by `src/proxy.ts`. Its internal validation handles `?next=` destination sanitization correctly (via `sanitizeInternalRedirect`). If an OAuth or Supabase token exchange fails, it safely falls back to `/auth/login?error=...` which is caught by the proxy rewrite and displays the error securely on the English login page.

### Locale persistence
The original code hardcoded `/auth/login` links in the UI, which meant a user clicking "Sign In" from `/de/games` would be routed to `/auth/login` (which rewrites to English), losing their active locale context. I updated `UserAccountMenu` and `ProfileClient` to dynamically parse `useParams().locale` and inject it into the `href` (e.g. linking to `/${locale}/auth/login`). This ensures the user's active locale remains locked during authentication round-trips.

### Proxy
No modifications were required in `src/proxy.ts`. Its logic was inspected and verified to already handle the correct `NEXT_LOCALE` cookie behaviors, correctly exempt `/api/` routes, and properly rewrite root-level implicitly English URLs.
